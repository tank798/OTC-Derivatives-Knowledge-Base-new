# 中国场外衍生品法规知识库：项目整体逻辑说明

## 一、项目目标

系统以本地法规库为知识底座，先检索相关条文，再让模型基于这些原文整理回答，并展示法规名称、具体条文和官网链接。

处理流程如下：

```text
法规原件
→ 结构化正文
→ 按法规结构切成 Chunk
→ 建立 BM25 关键词索引和本地向量索引
→ 用户提问
→ Agent 使用 Flash 轻量改写问题，并请用户确认
→ Agent 用一个完整问题调用混合检索工具
→ Agent 阅读检索到的 Chunk，必要时再检索一轮
→ Agent 基于合并后的证据撰写回答
→ 程序校验引用 ID 和逐字原文是否真实
→ 回填法规元数据和官网链接
→ 返回“结论 + 理由 + 法规原文 + 官网链接 + 证据边界”
```

系统的核心是三件事：

1. 法规原件转换成结构化正文时保持内容完整和原意一致；
2. 用户提问后召回真正关键的Chunk；
3. 模型引用均来自本次检索结果，程序校验法规与原文的对应关系。

## 二、法规库里有什么

当前正式知识库包括：

- 216 份正式纳入的法规原件（原始目录另有2份仅归档的内嵌附件）；
- 216 份结构化正文；
- 2,642 个正式 Chunk；
- 216 份法规均配置官网链接；
- Chunk ID 唯一，且每个 Chunk 都能追溯到所属法规和结构化原文块。

静态的[场外衍生品法规知识库](../../deliverables/场外衍生品法规知识库_20260727.html)可以查看：

- 法规名称、文号、发文主体和发布日期；
- 每份法规的规范化正文；
- 法规的官网链接；
- 按关键词、发文主体和收藏状态筛选；
- 收藏、正文编辑和个人标注。

法规的发布主体主要包括：

- 中国证监会；
- 中国证券业协会；
- 中国证券投资基金业协会；
- 中国期货业协会；
- 上海证券交易所和深圳证券交易所；
- 中国人民银行；
- 国家金融监督管理总局及其历史承接机构；
- 中国银行间市场交易商协会和中国外汇交易中心；
- 国务院和国家法律。

查看器中的发文主体筛选仅用于浏览；法规详情仍完整保留原始发文主体字段。

## 三、法规原件如何变成结构化正文

原始法规包括 PDF、DOC 和 DOCX。不同格式先由对应解析器读取，再统一整理成结构化 JSON。

这一层主要处理：

1. 提取正文、表格、Word 文本框和 smartTag 中的有效内容；
2. 识别标题、文号、发文机关、发布日期、施行日期和效力状态；
3. 识别章、节、条、款、项、附件和表格；
4. 删除真正的目录、重复页眉页脚和孤立页码；
5. 合并 PDF 跨行、跨页导致的句内换行，但保留条款和列表边界；
6. 检查扫描页、乱码、私有区字符和公式丢失；
7. 给每个结构化原文块分配 `source_block_id`。

发布套语、独立文号、重复封面标题和正文结束后的来源链接会按结构位置移入元数据或前置区；每份结构化JSON保留清洗规则版本、被移出的原文、清洗前后字符数以及原文/清洗后哈希，便于判断切分和向量更新范围；正式条款中的文号、引用和生效条款按正文结构完整保留。

原始法规作为只读输入。清洗、排版恢复和层级整理都发生在结构化层，原件保持完整。

## 四、Chunk 如何切分

长篇法规先识别层级，再按语义单元切分为可定位、可精确引用的Chunk；整份文件通过结构化索引参与检索。

边界优先级是：

```text
新文件或新分部
→ 章、节
→ 完整条款
→ 完整款、项或列表
→ 附件和表格
→ 完整句子和明显主题边界
```

当前长度约束大致为：

- 目标长度约 600 个正文字符；
- 一般上限约 1,200 个正文字符；
- 低于200字的非独立完整条款优先和相邻内容合并。

长度只是约束，完整语义优先。系统尤其保护：

- “包括以下内容”“应符合下列条件”等引导语与列表保持在同一语义块；
- 完整句子按句法边界切分；
- 表格按完整行处理，单元格内容保持完整；
- “依照前款”“除前项外”等依赖前文的内容保留必要上下文；
- overlap按语义依赖使用，避免机械滑窗重复。

每个 Chunk 除了正文，还保留：

- `chunk_id`、`document_id` 和文档内顺序；
- 法规名称、文号和发文机关；
- 发布日期、施行日期和效力状态；
- 章、节、条款范围和附件名称；
- 官网链接；
- 对应的 `source_block_id`；
- overlap来源和超长语义单元标记。

## 五、BM25 关键词检索

BM25 擅长找：

- 法规名称和文号；
- 专业术语；
- 数字、比例、金额和期限；
- “不得”“应当”“除外”等明确措辞。

中文文本使用NFKC规范化、中文双字切分和场外衍生品领域词识别。标题、章节、条号和正文进入同一个索引，发文机关字段保持统一权重。

BM25 的优点是对原文用词和数字非常敏感；局限是用户的口语表达可能和法规正式语言不同。

## 六、向量检索

向量检索用于找“说法不同，意思相近”的 Chunk。例如，用户说“券商收益凭证做雪球”，法规可能写的是“证券公司发行浮动收益凭证”“挂钩标的”“内嵌衍生品”或“敲入敲出”。

当前本地向量模型为 `Xenova/bge-base-zh-v1.5`，768维，q8量化。它负责把问题和Chunk转成可比较的向量，法律结论由Agent结合法规证据生成。

Chunk内容改变后同步重新生成向量，确保向量与当前Chunk一一对应。

## 七、混合检索

每次 `hybrid_regulation_search` 工具调用会同时执行：

1. BM25 取前 30 条；
2. 向量检索取前 30 条；
3. 用等权 RRF 融合两个排名；
4. 同一法规最多保留3个得分最高的 Chunk，避免单一长法规占满10条回答上下文；
5. 去重，并补齐必要的前置条款和 overlap 上下文；
6. 返回最多 10 个 Chunk 给 Agent。

RRF可以理解为“排名投票”。同一个Chunk在关键词和语义检索中都靠前，融合后通常也会靠前；两套排名按统一规则融合。

## 八、对话式法规 Agent

### 1. Agent 结构

当前采用连续对话的DeepSeek Agent。问题改写和Wiki确认等轻任务使用Flash，证据判断与回答使用Pro。System Prompt定义目标、工具和行为边界；Agent根据完整对话和工具结果决定下一步。

### 2. 先改写问题，再让用户确认

新对话的第一轮，Agent专注问题改写并呈现给用户确认；改写保留用户原意，同时明确主体、产品、行为和待解决的法规问题。

用户的回复由同一个 Agent 按自然语言理解：

- 如果用户确认，Agent 使用已改写的完整问题检索；
- 如果用户直接给出了修正后的问题，Agent 使用新问题；
- 如果用户只说“不对”却没有说正确问法，Agent 继续追问。
- 如果用户明确纠正上一回答并给出新的业务口径，Agent 先展示 Wiki 候选；只有用户再次确认后才写入。

### 3. 检索一个完整问题

确认后，Agent每轮把一个完整问题传给混合检索，由检索工具统一完成关键词与语义召回。

第一轮返回最多 10 个 Chunk。Agent 阅读这些内容后，根据证据判断：

- 哪些 Chunk 与问题相关；
- 现有证据是否足够回答；
- 如果不足，到底缺少什么直接规定；
- 是否能用一个更准确的完整问题再检索一轮。

检索最多执行两轮。第二轮同时列出第一轮中仍相关的evidence ID，系统保留这些原文并加入第二轮新结果；合并后的最终上下文最多10个Chunk，保证证据连续和上下文规模稳定。

### 4. 证据不足的处理

如果当前法规只规定了一般条件，Agent会先标注具体产品结论所需的直接依据，并依据证据强度组织回答。

这时回答可以是：

> 根据当前知识库检索到的法规，无法得出确定结论。现有条文明确了……，但并未直接规定……。

然后列出相关法规、逐字条文、官网链接和待补充的信息；最终回答按证据强度呈现确定结论或边界说明。

### 5. 回答如何组织

Agent 提交的回答包含：

1. 直接结论；
2. 通俗、可核验的理由摘要；
3. 它选择的 evidence ID；
4. 从对应 Chunk 中连续逐字复制的原文；
5. 每条原文与用户问题的关系和边界；
6. 回答实际使用的专家Wiki条目；未使用时明确标记为空。

模型提交evidence ID和逐字原文；法规标题、文号、发文机关、条号、效力状态和官网URL由系统根据evidence ID从真实Chunk元数据回填，确保引用与法规原文一一对应。

## 九、程序只检查引用真实性

最终回答由同一Agent完成，程序化校验聚焦引用真实性：校验evidence ID、逐字引文和法规元数据与最终上下文的一致性；法律结论由业务人员结合证据复核。

`CitationValidatorService` 只检查三件客观可确定的事：

1. evidence ID 是否真的属于本次提供给 Agent 的最终 Chunk 上下文；
2. `quoteExact` 是否是对应 Chunk 中的连续逐字原文；
3. 法规名称、文号、发文机关、条号、效力状态和官网链接是否由该 evidence ID 的真实元数据回填。

第一次校验失败时，程序把具体错误返回给Agent，执行一次定向ID或引文修订；第二次校验仍失败时结束修订流程并保留失败状态。

## 十、三个真实问题如何理解

下面的三道问题是手动测试示例，统一经过用户确认、通用Agent和混合检索链路。

### 1. 上市公司可以做挂钩自己本身标的的场外衍生品吗？

这个口语问题需要弄清“自己本身标的”是不是指上市公司自身发行的股票，以及场外衍生品的交易对手是证券公司、期货风险管理公司还是其他持牌机构。检索到的现行条文和已公布但尚未施行的统一办法，还需要区分生效时间。

回答按交易对手类型分别展示相关制度及其适用范围，保持禁止性规定的适用边界。

### 2. 券商收益凭证可以做雪球吗？

当检索结果覆盖浮动收益凭证的一般发行、挂钩标的、业务资格、损失结构和信息披露规则时，Agent先核对是否存在“雪球收益凭证可以发行”或“不得发行”的直接条文，再组织确定性结论。

更合理的回答是：说明当前检索结果无法支持一个普遍、确定结论，再列出现有法规已经规定的一般边界、具体条文和官网链接，由业务人员结合产品结构和最新监管口径继续判断。

### 3. 私募产品投资雪球比例的范围有明确规定吗？

需要先区分口语中的“私募产品”到底是不是私募证券投资基金。《私募证券投资基金运作指引》对带敲入和敲出结构的场外期权或收益凭证，包括雪球结构，有明确的 25% 原则上限和严格例外条件。

这一规则直接适用于私募证券投资基金；其他私募股权基金、资产管理计划或私募产品按各自适用法规单独核实。

## 十一、日志和手动测试

每个聊天会产生独立的 `sessionId` 和 `runId`。服务端把运行过程写入 `data/index/eval/logs/`，包括：

- 用户每轮输入；
- Agent 每次选择的工具；
- 检索问题、检索目的、命中 Chunk 和 BM25 / 向量 / RRF 排名；
- 第二轮保留的第一轮证据；
- 引用校验失败的具体原因；
- 最终回答、采用的 evidence ID、模型调用次数和每次耗时。

日志目录由Git忽略，API Key和长法规上下文保留在本地运行环境。

三道真实问题用于手动链路验证。启动本地API和聊天页面后，按真实用户对话测试，并结合页面回答和运行日志定位改写、检索、证据保留和引用生成环节。

## 十二、系统边界与可靠性

系统可靠性建立在以下分层措施之上：

```text
原件负责提供真实内容
结构化层负责保持正文、表格和层级
Chunk 层负责提供合适的检索单位
BM25 负责找准专业词、原文措辞和数字
向量模型负责理解近义和口语表达
RRF 负责融合两类排名
主 Agent 负责理解用户、选择工具、判断证据和组织回答
引用校验负责阻止伪造 evidence ID 和伪造逐字原文
人工判断最终处理法律结论、业务事实和监管口径的边界
```

必要的程序上限用于控制调用和上下文规模：最多两轮检索、最多10个最终Chunk、最多一次引用修订；所有问题共用同一套边界。

最后，本系统提供法规检索、原文引用和证据整理；最终法律意见和金融机构内部合规审批由业务人员完成。

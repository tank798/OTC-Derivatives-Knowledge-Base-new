# GitHub 项目说明与截图清单

这份文档服务于 GitHub 首页展示，不是系统运行手册。目标是让第一次打开仓库的人在 3 分钟内看懂：项目为什么做、用户怎么用、核心链路怎么保证可追溯，以及下一步如何在本地运行。

## 一、GitHub 页面应该放什么

### 1. README 放“故事”和“结果”

仓库根目录的 `README.md` 是 GitHub 首页，适合放：

- 一句话定位：这是一个什么系统；
- 业务痛点：为什么不能只靠大模型记忆；
- 当前规模：法规数量、Chunk 数量、官网链接数量；
- 一张从原件到回答的流程图；
- 4—5 个真正有差异的能力；
- 3—4 张关键截图；
- 真实问题示例和证据不足边界；
- 本地启动命令；
- 指向详细架构、审查报告和截图清单的链接。

README 不适合塞入每个测试日志、每次 Prompt 修改的全文或完整法规原文。那些内容放在 `docs/`，通过链接让感兴趣的人继续深入。

### 2. `docs/` 放“证据”和“操作说明”

建议长期保持下面的分工：

```text
README.md                         GitHub 首页：项目故事、亮点、截图、快速开始
docs/GitHub项目说明与截图清单.md   GitHub 展示维护：截图目录、命名、脱敏和拍摄步骤
docs/architecture/                业务流程与技术架构
docs/reviews/                     原文、Chunk、索引和质量核验报告
docs/项目迭代记录.md               每次改了什么、为什么改、如何验证
docs/assets/iterations/            已有的迭代截图
docs/assets/github/               建议新增的正式 README 截图
```

正式截图建议集中放在 `docs/assets/github/`。不要把截图散落在 `output/`、临时目录或个人桌面，否则 GitHub 页面链接容易失效，也不方便以后替换。

## 二、建议拍摄的 7 张图

截图不是越多越好。首页首屏建议 4 张，另外 3 张放到“深入了解”或项目文档中。

| 编号 | 建议文件名 | 放在哪里 | 画面要回答的问题 |
|---|---|---|---|
| 01 | `01-chat-home.png` | README 首屏附近 | 这个产品长什么样，用户从哪里开始提问？ |
| 02 | `02-question-confirmation.png` | README“先确认问题” | Agent 如何把口语问题整理后交给用户确认？ |
| 03 | `03-retrieval-progress.png` | README“混合检索” | 用户能否看到 BM25、向量、RRF 和证据阅读过程？ |
| 04 | `04-answer-and-sources.png` | README“回答与法规依据” | 回答和右侧完整法规原文如何对应？ |
| 05 | `05-regulation-viewer.png` | README“知识库” | 216 份法规和 Chunk 如何浏览、筛选和核对？ |
| 06 | `06-badcase-wiki.png` | 详细文档 | 用户反馈如何进入 Badcase，Know-how 如何确认后写入 Wiki？ |
| 07 | `07-chunk-and-formula.png` | 详细文档 | 条款边界、表格和公式如何保真展示？ |

建议统一使用桌面宽屏截图，推荐 1440×900 或 1600×1000；同一组截图尽量使用同一个浏览器窗口尺寸、相同缩放比例和相同主题。移动端截图可以单独放在文档末尾，不要和桌面图混排。

## 三、每张图具体怎么截

### 01：聊天首页

**要展示：** 左侧新对话和历史记录、中间输入框、简短产品名称，页面整体留白和布局。

**操作：**

1. 启动 API 和 Web；
2. 打开 `http://127.0.0.1:3000`；
3. 新建一个空对话，不要让历史问题遮住输入框；
4. 浏览器缩放恢复到 100%；
5. 截取完整页面，不要截操作系统桌面或终端。

**构图：** 输入框放在画面下方偏中间，左侧导航完整但不需要显示过多历史问题。

### 02：问题确认卡片

**要展示：** 用户输入“券商收益凭证可以做雪球吗？”后，Agent 整理出更清楚的问法，并出现“确认并检索”和“修改问题”。

**操作：**

1. 输入一个真实问题；
2. 等待改写完成；
3. 在用户确认前截图；
4. 确认卡片里不要出现 API 错误、调试 ID 或本地文件路径。

**构图：** 保留右侧留白，突出问题卡片；不要把整段原始法规上下文截进来。

### 03：检索处理过程

**要展示：** 页面显示“正在进行中”，并能看到问题确认、BM25 关键词排序、向量语义排序、混合结果整理和证据阅读等过程。

**操作：**

1. 先确认问题；
2. 在回答尚未完成时截图；
3. 如果模型响应过快，可以使用一个较长但与项目相关的问题，保证进度状态有足够时间出现；
4. 不要为了截图故意制造 network error。

**构图：** 让处理步骤位于回答区域中部，计时器和呼吸式动效可见，但不要出现长篇错误堆栈。

### 04：回答与右侧法规依据

**要展示：** 回答的直接结论、分析段落、右侧“法规依据”栏、至少一条完整引用原文和官网链接。

**操作：**

1. 使用有明确法规依据的问题，例如私募证券投资基金投资雪球结构的比例限制；
2. 等回答完成；
3. 展开右侧引用卡片；
4. 确保可以看到法规名称、文号或条款范围、完整 Chunk 原文和官网链接；
5. 不要显示内部 Chunk ID、API 调试信息或“引用校验已完成”等内部过程文字。

**构图：** 左侧回答和右侧依据都要保留，不要只截右栏。回答正文建议展示结论开头和一段分析，避免整页文字缩得太小。

### 05：法规知识库查看器

**要展示：** 左侧发文主体—法规层级、顶部筛选器、右侧法规正文切片，以及一个展开的 Chunk。

**操作：**

1. 打开 `docs/场外衍生品法规知识库0720.html`；
2. 选择一个法规数量较多的发文主体；
3. 展开一份包含多个 Chunk 的法规；
4. 展开一个包含条款正文或表格的 Chunk；
5. 如使用本地文件截图，确认页面没有显示浏览器地址栏中的私人目录。

**构图：** 左侧层级和右侧正文各保留足够宽度；筛选器不要处于展开遮挡状态。

### 06：Badcase 与专家 Wiki

**要展示：** 用户反馈记录的问题、回答、参考依据三段结构，以及 Wiki 候选需要用户确认后才能写入的流程。

**操作：**

1. 对一条回答点击“需要改进”；
2. 填写简短反馈；
3. 打开左下角菜单进入 Badcase 工作台；
4. 截取待复核卡片；
5. 如要展示 Wiki，使用脱敏后的示例 Know-how，不要把真实客户、交易或内部人员信息放进截图。

**构图：** 优先展示卡片之间的分隔和“待复核”状态，不需要截整个空白工作台。

### 07：Chunk、表格和公式

**要展示：** 一条结构清晰的条款、一个表格或一个公式，以及它对应的法规名称和条款范围。

**操作：**

1. 在法规查看器里搜索“公式”“比例”或具体条号；
2. 展开对应 Chunk；
3. 确保公式没有被截断，表格列没有完全挤成一行；
4. 如需要局部放大，可再截一张局部图，但 README 不建议放太多细节图。

## 四、截图命名与存放

先创建目录：

```bash
mkdir -p docs/assets/github
```

截图完成后统一放入：

```text
docs/assets/github/01-chat-home.png
docs/assets/github/02-question-confirmation.png
docs/assets/github/03-retrieval-progress.png
docs/assets/github/04-answer-and-sources.png
docs/assets/github/05-regulation-viewer.png
docs/assets/github/06-badcase-wiki.png
docs/assets/github/07-chunk-and-formula.png
```

README 中使用相对路径引用，例如：

```markdown
![回答与法规依据](docs/assets/github/04-answer-and-sources.png)
```

不要使用本机绝对路径，例如 `/Users/castle/...`；这种链接只在本机有效，推到 GitHub 后会全部失效。

## 五、截图脱敏清单

提交前逐张检查：

- 没有 API Key、Token、Cookie、`.env` 内容；
- 没有客户名称、账户、交易编号、手机号、邮箱或内部网址；
- 没有个人桌面、终端窗口、Finder 路径和本地用户名；
- 没有未经授权的完整法规原件截图；展示条文时以知识库页面和官网链接为主；
- 没有模型内部 Prompt、系统消息、隐藏工具参数或调试堆栈；
- 计时器、日志和请求 ID可以保留，但不要让它们成为画面主角；
- 图片中文字足够大，GitHub 页面缩略查看时仍能看清核心信息。

## 六、推荐的 README 图片顺序

README 首页建议按以下节奏排列：

1. 一句话定位和项目规模；
2. 一张流程图；
3. `01-chat-home.png`，让读者先认识产品；
4. `02-question-confirmation.png`，解释 Agent 如何理解问题；
5. `04-answer-and-sources.png`，展示最终价值；
6. `05-regulation-viewer.png`，证明知识库可人工核对；
7. 运行方式、架构文档和质量报告链接。

`03-retrieval-progress.png`、`06-badcase-wiki.png` 和 `07-chunk-and-formula.png` 可以放在 README 后半段或项目文档中，避免首屏信息过载。

## 七、何时重新截图

只有发生以下变化时才需要更新正式截图：

- 页面布局、字体、颜色或依据栏交互发生明显变化；
- 回答输出结构改变；
- 左侧历史对话、Badcase 或 Wiki 流程改变；
- 法规查看器的筛选层级或 Chunk 展示方式改变；
- README 中展示的规模数字发生变化。

每次更新时，在 `docs/项目迭代记录.md` 增加日期、变化原因和截图文件名；不要用一张新图覆盖旧版本而不留下记录。
